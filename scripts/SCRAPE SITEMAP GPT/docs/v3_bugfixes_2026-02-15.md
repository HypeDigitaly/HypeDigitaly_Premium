# V3 Bug Fixes -- 2026-02-15

10 bug fixes applied across 6 modules in the GPT Scraper V3 codebase. These were discovered during a thorough code review and address critical URL blacklisting bypasses, CLI override inconsistencies, XML sitemap parsing gaps, and a configuration cleanup.

## 1. Blacklisting Fixes

### 1.1 `is_url_blacklisted_by_path()` -- Four sub-bugs (utilities.py)

**File:** `gpt_scraper_v3/utilities.py`, lines 125-141

**Root cause:** The path-based blacklist matching function had four distinct failure modes that could allow blacklisted URLs to be processed:

1. **Percent-encoding bypass.** A URL containing `%C3%A1` (encoded `a`) would not match a blacklist entry written as `/aktuality` because the raw path bytes were compared without decoding.

2. **Trailing-slash mismatch.** A blacklist entry `/sekce/archiv/` would not match the URL path `/sekce/archiv` (no trailing slash) or vice versa.

3. **False-positive prefix match.** A blacklist entry `/aktuality` would incorrectly match `/aktualityXYZ` because `startswith()` was used without requiring a slash boundary after the prefix.

4. **Empty-entry crash risk.** If a config file contained an empty string `""` in the `blacklisted_relative_url_paths` array, every URL would match because `startswith("")` is always `True`.

**What was fixed:**

```python
def is_url_blacklisted_by_path(url: str, blacklisted_paths: List[str]) -> bool:
    parsed = urlparse(url)
    url_path = unquote(parsed.path).rstrip("/")       # decode + strip slash
    for bl_path in blacklisted_paths:
        normalized_bl = unquote(bl_path).rstrip("/")   # decode + strip slash
        if not normalized_bl:                           # skip empty entries
            continue
        # exact match OR prefix with slash boundary
        if url_path == normalized_bl or url_path.startswith(normalized_bl + "/"):
            return True
    return False
```

### 1.2 Missing path-based blacklist check in `extract_links()` (sitemap_parsing.py)

**File:** `gpt_scraper_v3/sitemap_parsing.py`, line 317

**Root cause:** The deprecated `extract_links()` function only checked `cfg.BLACKLISTED_URLS` (exact-match list). It did not call `is_url_blacklisted_by_path()`, so URLs matching a relative-path blacklist entry would slip through when legacy HTML parsing mode was used via `--legacy-html-parsing`.

**What was fixed:** Added `is_url_blacklisted_by_path()` as a compound condition alongside the existing exact-match check:

```python
if absolute_url in cfg.BLACKLISTED_URLS or is_url_blacklisted_by_path(
    absolute_url, cfg.BLACKLISTED_RELATIVE_PATHS
):
```

The import of `is_url_blacklisted_by_path` was also added to the module's imports at line 18.

### 1.3 Missing path-based blacklist check in `parse_generic_feed()` (rss_feeds.py)

**File:** `gpt_scraper_v3/rss_feeds.py`, line 397

**Root cause:** The generic RSS feed parser only checked `cfg.BLACKLISTED_URLS`. Any feed URL matching a relative-path blacklist pattern would be processed.

**What was fixed:** Added `is_url_blacklisted_by_path()` to the compound filtering condition:

```python
if (
    absolute_url.startswith(cfg.BASE_URL)
    and absolute_url not in cfg.BLACKLISTED_URLS
    and not is_url_blacklisted_by_path(absolute_url, cfg.BLACKLISTED_RELATIVE_PATHS)
    and absolute_url != rss_url
):
```

The import was also added at line 18.

### 1.4 Missing path-based blacklist check in `extract_links_from_jina_summary()` (content_fetching.py)

**File:** `gpt_scraper_v3/content_fetching.py`, lines 19, 467

**Root cause:** The Jina AI link extraction function only checked `cfg.BLACKLISTED_URLS`. This is the primary HTML sitemap parsing path (non-legacy mode), so the gap affected the default scraping workflow.

**What was fixed:** Added `is_url_blacklisted_by_path` to the import block and to the blacklist check:

```python
if absolute_url in cfg.BLACKLISTED_URLS or is_url_blacklisted_by_path(
    absolute_url, cfg.BLACKLISTED_RELATIVE_PATHS
):
```

## 2. CLI Fixes

### 2.1 `--base-url` override does not recompute derived URL fields (cli.py)

**File:** `gpt_scraper_v3/cli.py`, lines 10, 134-177

**Root cause:** When a user passed `--base-url` on the command line, `apply_cli_overrides()` updated `cfg.BASE_URL` but did not recompute five derived fields that are computed from `BASE_URL` during `load_configuration()`:

- `PARSED_BASE_URL` -- the `urlparse()` result
- `BASE_NETLOC` -- the network location (e.g., `www.example.cz`)
- `NON_WWW_BASE_NETLOC` -- the netloc without `www.` prefix
- `BASE_SCHEME` -- `http` or `https`
- `CANONICAL_BASE_URLS` -- the set of URL variants used for homepage detection

This meant that domain filtering, homepage detection, and canonical URL checks would all still use the original config-file values, causing unpredictable behavior when `--base-url` was used.

**What was fixed:** Added a block after the URL override loop that detects when `--base-url` was provided and recomputes all five derived fields. The recomputation logic mirrors the code in `load_configuration()` exactly:

```python
if getattr(args, "base_url", None):
    cfg.PARSED_BASE_URL = urlparse(cfg.BASE_URL)
    cfg.BASE_NETLOC = cfg.PARSED_BASE_URL.netloc
    cfg.NON_WWW_BASE_NETLOC = (
        cfg.BASE_NETLOC[4:] if cfg.BASE_NETLOC.startswith("www.") else cfg.BASE_NETLOC
    )
    cfg.BASE_SCHEME = cfg.PARSED_BASE_URL.scheme
    # ... full CANONICAL_BASE_URLS recomputation ...
    cfg.CANONICAL_BASE_URLS = canonical
```

The imports `urljoin`, `urlparse`, and `urlunparse` were also added to the module's import line (line 10).

## 3. XML Sitemap Parsing Fixes

### 3.1 Paged sitemap drops URLs without `<lastmod>` (xml_sitemap.py)

**File:** `gpt_scraper_v3/xml_sitemap.py`, lines 99-126

**Root cause:** The regex-based paged sitemap parser (`page=N` format) only matched `<url>` entries that contained both `<loc>` and `<lastmod>` elements. URLs without a `<lastmod>` element were silently dropped. This could cause large gaps in coverage for sitemaps where not all entries have modification dates.

Additionally, the original regex used `\s*` between `<loc>` and `<lastmod>`, which failed to match when arbitrary whitespace or other elements appeared between them.

**What was fixed:**

1. The `if last_modified:` guard was removed so that URLs with unparseable dates are still stored with `None` as their last-modified value.

2. A second regex pass was added to capture URLs that have `<loc>` but no `<lastmod>` element at all:

```python
# Match URLs WITH lastmod
url_matches = re.findall(
    r"<url>.*?<loc>(.*?)</loc>.*?<lastmod>(.*?)</lastmod>.*?</url>",
    page_response.text, re.DOTALL,
)
for url, lastmod in url_matches:
    last_modified = parse_lastmod_date(lastmod)
    url_last_modified[url] = last_modified

# Also capture URLs WITHOUT lastmod (store None)
loc_only_matches = re.findall(
    r"<url>.*?<loc>(.*?)</loc>.*?</url>",
    page_response.text, re.DOTALL,
)
without_lastmod = 0
for url in loc_only_matches:
    if url not in url_last_modified:
        url_last_modified[url] = None
        without_lastmod += 1
```

3. The regex patterns were updated from `\s*` to `.*?` with `re.DOTALL` to handle arbitrary content between XML elements.

4. The log message was updated to accurately report both counts:

```python
logger.info(
    "Extracted %d URLs (%d with lastmod, %d without) from %s",
    page_total, len(url_matches), without_lastmod, page_url,
)
```

## 4. Configuration Cleanup

### 4.1 Duplicate `BLACKLISTED_RELATIVE_PATHS` assignment (config.py)

**File:** `gpt_scraper_v3/config.py`

**Root cause:** The `BLACKLISTED_RELATIVE_PATHS` field was assigned twice during `load_configuration()`. The second assignment (which was at the former line 420) was redundant and identical to the first. While not a runtime bug, it was a maintenance hazard: a future developer might change one assignment without noticing the other, leading to confusion about which value takes effect.

**What was fixed:** The duplicate assignment was removed. The single assignment remains at line 388:

```python
cfg.BLACKLISTED_RELATIVE_PATHS = raw["website"].get("blacklisted_relative_url_paths", [])
```
